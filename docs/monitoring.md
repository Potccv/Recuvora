# 通用监控与真实故障管理

本功能消费独立节点或宿主侧业务插件的只读观测，执行配置指定的规则，并持久记录目标故障和监控覆盖问题。节点接入复用现有 [JSONL 协议](extension-protocol.md)，节点程序及本机采集实现由外部项目交付。

监控输出不产生执行许可，也不调用修复模型或文件执行器。故障解除表示所配置的异常条件已通过新观测解除，不表示 Recuvora 已完成某次修复或验证了全部业务。

## 组成与状态

- `monitors`：通用目标发现、轮询调度、观测规范化、规则比较、连续样本判定、数据时效和覆盖检查。
- `nodes` / `protocol`：外部契约匹配、只读调用、限额、超时、取消及传输进程回收。
- `recovery::incidents`：故障归并、人工确认、观测检查点和持久恢复，独立于封闭模拟引擎和审批存储。
- `boot::host`：将监控注册为依赖外部服务注册表的框架服务，统一启动及关闭。
- 官方控制台：监控状态、故障列表、单条证据及确认收到；使用认证 HTTP API。

目标判断、观测新鲜度和采集覆盖分别表示。一次节点连接成功不能证明目标健康；成功读取空日志批次只能说明检查了相应范围。缺失、过期、格式错误或失联会使目标判断成为未知；已打开的目标故障保留，不能因没有数据而自动解除。

规则比较成立表示健康。布尔、字符串支持等于/不等于，数值支持等于、不等于及大小比较，数值限于 ±2^53。规则通过 JSON pointer 选择观测中的字段，并分别配置确认异常和确认恢复所需的连续有效样本数。缺少字段、类型不匹配或覆盖缺口打断连续计数。故障信号保存规则及观测证据，不能把节点返回的文本当作指令。

## 通用目标发现与配置

`MonitorsConfig` 支持固定 `monitors` 和可选 `discoveries`。固定项适合预先明确的目标；发现项轮询配置允许的只读清单方法，将目标键注入部署者审查的固定观测模板。宿主不识别某个采集器的业务目录或配置格式，清单提供方负责验证自己的目标。

清单返回以下通用形状，每个目标只能提供一个安全键：

```json
{
  "schema_version": 1,
  "complete": true,
  "targets": [{"key": "target-001"}],
  "error": null
}
```

键为 1–64 个 ASCII 字母、数字、下划线或连字符，同批唯一，最多 64 项。清单不能提供方法、规则、目标属性或授权事实。错误与不完整清单必须明确报告；成功扫描后没有目标可以返回完整空清单。

下面展示通用宿主配置结构，契约和参数名称由实际提供方定义：

```json
{
  "schema_version": 1,
  "monitors": [],
  "discoveries": [{
    "id": "discovery-001",
    "extension_id": "observation-extension",
    "contract": "com.example.observation",
    "version": 1,
    "method": "inventory",
    "params": {},
    "interval_ms": 30000,
    "timeout_ms": 5000,
    "max_targets": 16,
    "parameter": "target_key",
    "template": {
      "id": "monitor",
      "target_id": "target",
      "source_id": "source",
      "extension_id": "observation-extension",
      "contract": "com.example.observation",
      "version": 1,
      "method": "observe",
      "params": {},
      "interval_ms": 30000,
      "timeout_ms": 5000,
      "stale_after_ms": 90000,
      "startup_grace_ms": 60000,
      "rule": {
        "pointer": "/ready", "operator": "eq", "value": true,
        "failure_samples": 3, "success_samples": 3
      }
    }
  }]
}
```

`discovery.id` 单独标识发现来源；`template.id`、`target_id` 和 `source_id` 是监控身份前缀。对于 `target-001`，示例生成 `monitor.target-001`、`target.target-001`、`source.target-001`，并在模板参数中加入 `"target_key":"target-001"`。注入字段不得已存在于 `template.params`，也不能是宿主保留的 `target_id`、`source_id`、`cursor` 或 `generation`。扩展白名单须允许清单和观测两个调用，现有只读契约与 schema 校验仍适用。

示例发现与观测分别每 30 秒轮询，周期可独立配置。新增名称在发现后获得独立监控和检查点；新目标还没有观测数据时保持未知。最多配置 8 个发现来源，固定监控数量加所有发现项的 `max_targets` 预留容量不得超过 64。容量按该发现来源曾登记的不同键累计，而非仅按当前在线目标计算；容量不足会显示错误，不清除旧身份或证据腾出空间。

完整清单中消失的键使旧监控成为未知，保留其故障、确认状态、游标和数据源检查点。同名重现时复用既有监控，不重复创建；改名产生新键，旧键继续保留。坏清单、不完整清单和调用失败不用于撤销其他已知目标，仍可接纳不完整清单内通过验证的新键。

已接受键集合有界持久化，先落盘再启动新监控。重启后恢复这些身份，当前存在性重新发现，不能沿用旧运行时状态证明健康。发现来源、模板或业务来源绑定发生变化时使用新的发现/监控身份；不将旧游标迁移到不同目标。此机制只登记配置授权范围内的只读监控，不安装插件或授予修复权限。

## 观测批次约定

第三方插件先登记自己的版本化契约，节点或插件实现已登记、被配置允许且声明只读的方法。该方法返回监控批次，不要求外部项目链接宿主 Rust crate。通用调用仍遵守非保留命名空间和现有 schema 子集约束。

调用参数包含配置中的业务参数，以及由宿主填写的 `target_id`、`source_id`、`cursor`、`generation`。配置不能覆盖这些关联字段。初次查询的游标和数据源代次为空；后续查询携带最后已持久处理的检查点。

```json
{
  "schema_version": 1,
  "target_id": "target-001",
  "source_id": "source-001",
  "generation": "source-generation-1",
  "cursor": null,
  "next_cursor": "record-1",
  "coverage": "complete",
  "has_more": false,
  "error": null,
  "samples": [
    {
      "id": "sample-1",
      "sequence": 1,
      "age_ms": 0,
      "value": {"ready": true},
      "evidence": {"kind": "provider-observation"}
    }
  ]
}
```

以上为契约载荷示例，外部契约 schema 必须允许这些字段，并落实类型和容量限制：

- `target_id` 和 `source_id` 必须与宿主选择匹配。
- `generation` 表示数据源连续性，不能因为每次协议进程启动就改变；源重置或丢失连续性时改变代次并明确缺口。
- `cursor` 对应本次请求，`next_cursor` 用于下一次读取；读取不能清空远端缓冲或隐式确认删除。
- 样本 ID 和序号在同一数据源代次中稳定；重复查询不应生成新的业务样本身份。
- `coverage` 和 `has_more` 描述是否完整及是否仍有积压；来源连续性丢失、分页未追上或保留期缺失不能标为完整当前覆盖。
- `age_ms` 为节点生成响应时观测已经经过的时间，宿主保守叠加本次请求耗时和接收后的单调时钟经过时间。无法确认年龄的历史数据不能证明当前健康。
- 空批次不制造健康样本；旧样本、重复样本不刷新当前健康的有效期或连续计数。

每次调用有截止时间，每个监控最多一个在途读取。独立的时钟检查负责发现缺失和过期，即使节点一直不返回也会更新监控覆盖。各监控共享有界资源；持续积压、限额拒绝或解析失败作为监控覆盖问题报告。

每批最多 32 条样本、256 KiB；每条 value/evidence 各最多 4096 字节、嵌套深度最多 24，整批两者合计最多 128 KiB。规则序列化最多 4096 字节。这些限额为故障证据和检查点的原子写入预留空间；批内倒序或身份冲突拒绝整批，保留上次检查点。

## 持久故障与确认

故障按监控、目标、规则及种类归并。种类分为目标异常和监控覆盖问题；同一未解除故障继续更新证据，新的异常发生在旧故障解除之后时创建新的故障记录。

- `open`：未确认的开放故障。
- `acknowledged`：操作员确认已看到或接手，故障仍然开放。
- `resolved`：新观测满足该故障的解除条件。

故障条件另有 `active`、`unknown`、`clear`，与操作员确认状态分开。采集断线只能使已有目标故障条件变成未知，不代表故障消失。人工确认必须携带当前 revision，操作员身份来自认证 HTTP 服务。过期 revision 返回冲突；客户端重新读取详情后才能再次决定，POST 不自动重试。

监控检查点、已处理游标及本轮故障变化在同一条持久事务中写入，同步成功后才更新内存状态。重复提交相同监控序号和相同内容幂等，冲突内容或跳号拒绝。这样，读取后宿主退出可以从最后已确认位置重读，故障不会因游标先推进而丢失。

运行目录位于源码之外，使用单写入者锁和有界 JSONL 日志。完整记录损坏、末尾残片、非法状态迁移或存储不可写都会拒绝继续变更；达到容量时报告不可用，不静默丢弃证据。存储暂不提供在线压缩、清理、迁移或分布式共识。

宿主重启重新建立当前监控状态并采样，不沿用上次进程的单调时钟或连续健康计数。已持久故障和游标保留，未知故障不会自动解除。关闭先拒绝新轮询和人工确认，再请求取消并排空在途读取，最后释放存储锁。

## API 与部署

控制台配置增加可选 `monitors_config`，指向源码之外的监控配置。监控状态和故障数据位于控制台 `data_dir` 下的 `monitoring` 目录。省略该配置时监控未配置，不使用演示数据补足。

新增权限为 `monitor.read`、`incident.read` 和 `incident.acknowledge`。持续后台采集由可信宿主配置启用，不依赖某个浏览器页面存活；UI 读取权限不自行启用监控或授予目标动作权限。

| 方法与路径 | 内容 |
| --- | --- |
| `GET /api/v1/monitors` | 已配置状态、监控摘要、发现来源摘要和运行错误 |
| `GET /api/v1/monitors/{id}` | 单条监控状态 |
| `GET /api/v1/incidents` | 故障摘要；支持 `cursor`、`limit` 和 `status` |
| `GET /api/v1/incidents/{id}` | 故障完整证据、revision 和允许动作 |
| `POST /api/v1/incidents/{id}/acknowledge` | `{ "revision": 1, "note": "已接手检查" }`，同步持久化后返回当前记录 |

故障列表默认查询仍开放的记录，`status` 可为 `active`、`all`、`open`、`acknowledged`、`resolved`。每页默认 25，最大 100，按不可变故障 ID 降序使用游标翻页。摘要不携带完整证据，详情按需读取。确认接口不创建通用执行操作、不解除故障、也不派发修复。

监控列表的 `discoveries` 包含发现来源的 `id`、运行状态、最近接收时间、`complete`、`known_targets`、`present_targets` 和 `last_error`。`known_targets` 包括已持久登记但目前缺失的名称；`present_targets` 表示当前发现状态，不能替代各监控的健康判断。

## 验证范围

自动检查应覆盖重复及乱序样本、陈旧数据、空批次、覆盖缺口、连续判定、重启、原子游标提交、故障归并和解除、权限及旧 revision、日志损坏与容量、关闭排空，以及实际外部协议轮询。目标发现额外覆盖空安装后新增、多目标隔离、坏/重复/不完整清单、容量、删除与重现、成员持久化、已确认故障和游标保留，以及无监控时的超时与关闭排空。

自动检查覆盖配置解析、规则与时效、动态发现、目标隔离、删除与重现、持久检查点、故障确认、关闭排空及外部协议夹具。检查结果与未覆盖边界汇总在[实现状态](implementation-status.md)。

这些检查不包含具体受监控产品、活动配置、提供方集成、跨项目部署或业务恢复。目标专属采集器、业务行为判定、自动诊断修复和完整业务恢复由对应集成项目独立实现与验证。
