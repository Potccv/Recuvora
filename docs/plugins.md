# Recuvora 插件设计

**Harness 提供方统一由独立节点实现。** 宿主只保留供应商中立的 `remote-node` 代理，不编译提供方进程或私有协议适配器。

> 状态：完整插件体系的目标设计。当前[通用框架原型](../src/framework/README.md)已实现本地服务、依赖与生命周期的受限子集，[Harness 接入](../src/harnesses/README.md)支持多实例 registry、通用节点代理与受控宿主工具路由，[受限修复](approval.md)已接通独立审批角色、持久许可及白名单文本动作；另已实现可信外部程序加载、JSONL 节点 Harness 代理、只读第三方契约消费及宿主渲染的声明式插件监控专页。其他本机平台执行后端、插件市场/签名发行格式、在线升级、通用远程写许可和完整部署仍待实现。业务与恢复边界见[架构设计](architecture.md)。

## 插件化的含义

Recuvora 以服务契约、依赖注入、事件扩展、实例生命周期和配置装配组合应用。框架提供通用机制，任务、授权、恢复日志和默认自愈流程由可信业务模块提供；监控、Harness、桌面、视觉和知识等能力依赖领域契约协作。

插件身份与源码模块、外部发行包、运行实例、工作进程、任务分别标识。一个模块或外部插件可以提供多个能力，一个工作进程可以承载多个可信实例；同一插件也可能在多个节点或会话中实例化。当前宿主采用单个 Cargo 包，模块划分不要求独立发行或独立进程；进程位置不是插件身份的定义。

| 注册来源 | 代码交付与启动 | 使用边界 |
| --- | --- | --- |
| 内置注册表 | 可信 Rust 模块与宿主共同编译发布，启动时登记元数据及构造入口 | 配置选择已有实现；新增代码须更新宿主，不支持任意外部代码热加载 |
| 独立插件包 | 安装描述元数据与产物，经来源、配置及权限校验后启动外部实例 | 默认进程外，使用版本化协议与代理接入服务契约；可独立发布 |

两类来源复用服务选择、依赖检查、能力权限及生命周期规则。内置调用可以直接使用类型化接口，不要求伪造进程握手或把每次调用序列化；进程外调用必须显式处理通信失败和不确定结果。

首版不将 Rust 原生动态库通用加载或 WebAssembly 运行时写成既定实现，不对其他第三方包及 API 提供隐式兼容承诺。需要 Rust ABI、沙箱或其他执行后端时另行评估，不通过目录命名暗示已支持。

## 外部节点与宿主侧业务插件

Recuvora 项目提供可信宿主、通用扩展机制、节点通信与开发约束，不提供节点程序、节点发行包或按能力裁剪的节点构建。单 Cargo 包约束只适用于宿主源码；Harness、日志采集等节点以及第三方宿主侧插件由独立项目构建、安装和发布，不要求依赖整个 `recuvora` crate，也不强制采用 Rust 或官方 SDK。

| 参与方 | 职责与交付边界 |
| --- | --- |
| 宿主核心及可信公共服务 | 提供注册、依赖、生命周期、连接、通用消息路由与限额；核验身份、兼容性和权限；按作用域维护明确的授权及权威记录服务 |
| 宿主侧业务插件 | 独立提供新增领域的版本化契约、消息 schema、解析和校验、事件消费、流程及业务结果验证；通过公共服务申请操作和记录事实 |
| 外部节点 | 实现并声明具体能力，管理本机依赖、资源与工作进程，检查实际目标和执行授权，采集或执行后报告证据与必要执行记录 |

“宿主侧”表示业务消费和编排角色，不表示与宿主同进程或共同编译。第三方独立安装插件默认进程外；同机部署的节点仍是独立程序。节点可以提供多个能力，一个业务插件也可消费多个节点，不要求插件、节点、能力和进程一一对应。

目标是新增业务通过“宿主侧插件 + 实现契约的外部节点”接入，无需为每个业务修改或重新编译宿主核心。前提是现有通用扩展协议和权限机制能够表达该业务；若需要新增核心协议或可信执行原语，仍须演进核心，不能用不受控的私有通道绕过它。只有契约文件、节点自报或通用消息转发，不能代替业务消费者和结果验证逻辑。

### 官方 UI 与插件监控专页

后台业务扩展与页面交付分别划分。统一监控/故障中心、Harness 会话、修复详情、日志查询、模拟实验室以及通用管理属于官方 UI 基础壳的标准页面，不能因为数据或执行能力来自插件，就要求用户另行安装对应页面插件。官方 UI 通过统一版本化服务契约访问内置服务、宿主侧业务插件及节点提供的能力，不复制后台授权、执行或权威状态逻辑。

宿主为每个配置的 `plugin` 提供 `#/monitoring/plugins/{id}` 专页。专页始终由官方静态资产渲染，先展示宿主掌握的插件连接状态、监控、发现与覆盖信息；插件声明缺失、不可用、无效或不可读时仍保留这份通用页面。统一监控与故障状态继续是宿主权威，插件专属内容只补充展示，不能修改健康、检查点、故障、授权或恢复事实。

插件可复用现有握手元数据登记一份可选的声明式监控视图：

1. `metadata.capabilities` 包含 `recuvora.monitoring_view.v1`。
2. 插件在自己的非保留命名空间契约中声明且只声明一个名为 `describe_monitoring_view` 的 `read_only` 方法。
3. 可信扩展配置的 `allow_calls` 明确列出该契约、版本与方法；能力字符串或方法声明本身不扩大调用许可。
4. 宿主固定以 `{"schema_version":1}` 调用该方法，且在这次描述调用中关闭插件可用于普通业务调用的节点回调；描述调用使用独立单槽，不占用普通业务和监控采集的调用容量。随后通过 `GET /api/v1/monitoring/plugins/{id}` 返回经复核的声明与宿主快照，浏览器不会直接连接插件。

声明版本 1 只允许标题、摘要以及有界的 `sections`。每个 section 用 `monitor_role` 选择宿主监控配置中相同 `view_role` 的快照，并用 `fields` 从 `MonitorSnapshot` 或其 `last_value` 按 JSON pointer 读取值。字段格式限 `text`、`number`、`boolean`、`timestamp_ms`、`duration_ms` 和 `json`，可带短单位与空值文案。例如：

```json
{
  "schema_version": 1,
  "title": "示例插件",
  "summary": "插件专属只读摘要",
  "sections": [
    {
      "id": "runtime",
      "title": "运行状态",
      "monitor_role": "status",
      "fields": [
        {
          "id": "task",
          "label": "当前任务",
          "source": "last_value",
          "pointer": "/task",
          "format": "text",
          "empty": "未提供"
        }
      ]
    }
  ]
}
```

宿主和浏览器都会检查完整字段集合、标识、JSON pointer、文本长度和总大小；当前上限为 32 KiB、8 个 section、合计 64 个 field。协议不提供 HTML、JavaScript、CSS、Markdown、URL、按钮或任意动作字段，所有字符串仅按纯文本展示，不会执行声明中的内容。字段值来自宿主已经取得的快照，插件不能借视图响应另报一套健康事实；`json` 展示中只要存在超过 JavaScript 安全整数范围的嵌套数值，整格即按空值处理，不能显示舍入后的伪精确结果。一个目标和角色匹配零个监控时显示空值，匹配多个时显示歧义，不由页面任选其一。

固定 GET 需要 `monitor.read` 才能读取通用插件页与宿主快照；只有同时具备 `extension.read` 时，宿主才调用已登记的 `describe_monitoring_view`。无该权限、方法调用失败或声明校验失败会返回明确的视图状态并降级到通用页面，不把专属内容缺失解释为目标健康或插件未配置。

监控所属业务插件与实际采集提供方分别记录。宿主以注册该业务契约的插件作为 `owner_plugin_id`，以监控的 `extension_id` 保留实际 provider；因此节点实现插件契约时，监控仍归入业务插件专页。`MonitorDefinition.view_role` 只参与专页展示匹配，不改变采集路由、规则、游标、检查点、故障或任何权限。

这是一种受限数据声明协议，不是任意第三方 UI、iframe、前端包或代码热加载机制。现有安装包管理、签名发行与在线升级限制保持不变。

### 契约注册与接入约束

以下为完整开发和验收要求。当前可运行的受限注册 API、JSONL v1 与 schema 子集见 [扩展协议](extension-protocol.md)，超出其范围的要求仍属后续设计：

- 插件声明自有命名空间、契约标识和版本、请求/结果/事件 schema、错误与未知结果语义。包版本、契约版本和通用传输版本分别管理；禁止覆盖保留契约或静默抢占其他插件的契约。
- 插件和节点分别声明提供/消费的契约、兼容范围、作用域、资源及权限需求。宿主校验已安装且获准的插件与已认证节点的匹配关系，再激活路由；节点不能通过能力声明触发下载或运行代码。
- 通用消息封装保留节点与插件实例、契约及版本、调用/任务/操作标识、目标与资源归属、期限和授权引用。业务负载由相应插件解释；身份、大小、速率和权限检查仍通过宿主公共边界完成。
- schema 通过只证明结构有效。插件提供业务含义、副作用类别、前置条件及核验规则，但声明和校验结果不自动产生执行许可。可信授权服务须按已批准的政策核验完整操作、契约版本和目标范围；无法解释授权范围或验证结果的动作保持关闭。
- 执行节点在副作用前再次检查授权、实际目标及操作关联，并按契约持久记录意图和结果。只读日志节点按其交付语义维护采集位置、缓冲和确认，不要求携带模型能力、写入能力或完整修复状态机。
- 缺少消费者插件、契约不兼容或权限不足时，相关能力不得进入业务执行；可保留有界能力摘要供诊断，不把未知负载作为已理解的业务事件处理。已在途的副作用先保留事实并核对，不能因插件卸载而遗失。
- 升级明确契约与状态的迁移、在途调用排空和回滚条件；不兼容时停用受影响依赖。断线、取消、确认丢失和重复消息保留调用关联及未知结果，不默认重新执行。

例如，独立日志节点上报某软件的日志；对应宿主侧插件定义该软件的事件契约、解释错误并提交受控处理流程。节点负责采集，插件负责业务含义，可信服务核验处理权限并保留权威事实。注册新业务不要求将该软件的 SDK 或采集实现编入宿主。

当前已实现可信 stdio/SSH 命令传输、独立插件进程注册新契约与只读消费，以及独立节点 Harness 代理。集中进程夹具覆盖缺失消费者、schema/命名空间/权限拒绝、工作区归属、双向工具和 Unknown。具体提供方协议与进程监督由节点项目维护；宿主尚未完成跨机器部署、自动重连或任意远程副作用迁移。

## 框架与业务契约

`src/framework/` 管理上下文、服务注册、依赖、事件、实例状态、资源清理及运行后端接口，不理解具体任务状态、授权政策或目标专属规则。`src/boot/` 解析配置并验证应用组合；`src/recovery/` 定义自愈业务规则与可信默认实现。

内置领域在模块内共同维护服务定义、提供方与消费者；外部新增领域由宿主侧业务插件维护契约及消费逻辑，由节点项目维护实际提供方。例如平台服务规定截图、会话和输入语义，各平台节点提供对应实现；流程调用服务接口，不导入某个平台实现的内部模块。SDK 复用公开接口，`src/protocol/` 承载通用消息及契约映射机制，不集中硬编码所有业务，也不形成第二套业务权威。

每项服务契约至少明确：

- 稳定标识、版本、作用域、调用与事件类型、结构化错误和可用性语义。
- 所需目标及任务上下文、权限检查位置、资源互斥和容量限制。
- 是否产生副作用、幂等与取消策略、未知结果的核验方式。
- 必需及可选依赖、兼容范围、提供方切换条件和资源释放责任。

任务、授权、调度与权威恢复日志的实现可以按受控配置组合，但同一作用域必须有明确且不冲突的权威提供者。生产组合在持久服务初始化、恢复对账及授权服务可用前不得开放执行；这些服务失效后暂停相关动作，不用知识索引或临时服务替代。

| 能力领域 | 主要输出 | 业务边界 |
| --- | --- | --- |
| monitors | 观测、故障与覆盖状态 | 不能把事件自行转成获准的修复动作；失联不表示健康 |
| harnesses | 诊断、方案、工具请求及受委托的结构化审批评估 | 评估由可信授权服务核验；不能自行扩大政策、产生执行许可或宣告业务恢复 |
| platforms、vision | 会话能力、画面、输入结果与识别证据 | 输入受任务及会话约束；识别置信度不等于执行许可 |
| actions | 变更、命令、发布、回退和验证证据 | 在执行边界核验授权、前置状态及资源所有权 |
| knowledge | 候选经验、检索与失效信息 | 不承担权威恢复，不扩大任务权限 |
| interfaces、notifications | 用户请求、人工决定及通知投递结果 | 身份和决定由授权服务核验；投递结果不改变任务事实 |

## 依赖、服务与事件

装配时根据服务标识、兼容版本、作用域及配置选择提供方。必需依赖缺失、不兼容或存在循环时保持等待或停用；多个候选提供方需要明确选择，权威服务不得静默覆盖或同时写入。可选依赖缺失必须有已声明的降级行为。

服务就绪后激活消费者，依赖变化时停止受影响调用并按策略排空、解绑和重新绑定。框架处理通用顺序，业务契约决定哪些变更必须停机恢复；授权和持久服务不允许在有未决任务时无条件热替换。

事件区分短暂观测、通知及持久业务事实。事件总线本身不保证持久性；重要事实应先由权威业务服务持久接收，再确认或触发后续动作。外部观测至少关联来源和时间，重复或过期消息不能重复推进任务。

事件订阅不授予权限，拦截或扩展流程也不能绕过授权和业务验证。服务注册、监听器、定时器、后台任务及资源以插件实例为所有者，通过 effect/dispose 风格的统一机制登记和清理；清理资源不等于回滚目标修改、发送或其他外部动作。

## 描述元数据与配置装配

内置模块的元数据来自可信编译注册表；独立包须提供启动前可读取的描述。完整发行包、签名及安装市场格式尚未选定，以下为目标信息要求；当前可信启动配置和握手字段以 [扩展协议](extension-protocol.md) 为准：

| 信息 | 要求 |
| --- | --- |
| 身份与版本 | 包标识、包版本、实例标识分别管理；服务、协议及私有状态版本不与包版本混用 |
| 能力与依赖 | 提供和消费的服务、兼容范围、必需或可选依赖、作用域 |
| 配置与权限 | 配置校验规则、所需资源、凭据引用、目标及会话限制；申请不等于授权 |
| 内置构造入口 | 仅引用宿主已登记的实现；不能由配置指定任意原生代码地址 |
| 外部运行入口 | 已验证产物、平台目标、进程入口、最小环境、协议范围及启动限制 |
| 状态与升级 | 状态格式、迁移条件、排空及恢复方式、支持的升级边界 |

独立包的入口必须解析到已验证产物，参数结构化传递；来源与文件完整性检查、签名及分发策略在实施前确定。安装、启用、能力权限和任务授权分别管理，发现文件或声明能力不代表获准执行。

上述包入口要求针对宿主安装并启动的插件。独立节点由其项目维护安装和启动；宿主接入配置只绑定节点身份、连接及能力范围，不代替节点包构建或安装管理。

`profiles/` 维护宿主组合示例；已实现 Harness、repair、扩展及控制台配置，完整部署 profile 仍待完善。组合选择插件实例、提供方、依赖、配置及接入范围，不负责构建或发布节点程序。节点自己的安装、启动和平台依赖由其独立项目维护。配置中的凭据使用受控引用，不能写入包描述或普通日志。

### 当前 Harness 与受限修复配置

以下描述宿主已有的供应商中立接入。第三方进程可按 [JSONL v1](extension-protocol.md) 独立注册业务契约并进行获准的只读消费；显式扩展配置启动已安装程序并注册其契约，但不负责下载安装。

Harness registry 已固定一个局部、版本化的有界 JSON schema；它不是通用部署 profile 或插件包格式。每个 Harness 实例包含稳定 ID、已注册适配器标识、由适配器解释的地址、启用状态和节点工作区 ID。多个实例可以复用同一适配器，调用通过实例 ID 或显式默认项选择；所选实例失败时不得静默转投其他实例。每次请求的节点和工作区归属都在派发前校验，真实目录范围由资源所在节点复核。

`repair` 使用独立的外部 JSON 配置选择执行实例、审批政策、目标根和文件白名单。执行与审批可引用同一 Harness ID，但必须创建独立会话并按角色分配权限；当前修复流程均使用 Hidden 会话，审批使用独立目录且无工具。适配器有 4 个执行槽及 2 个专用审批槽，防止执行等待审批时阻断审批本身。`recovery` 持久核验决定、政策范围、完整操作和期限，并提供一次执行许可；`actions` 在写入前复核目标与原内容。人工操作可由本地 CLI 或认证 HTTP 入口提交：前者使用操作系统用户身份，后者使用配置的单操作员身份及权限。完整契约和失败语义见 [审批说明](approval.md)，代码与自动验证边界见[状态表](implementation-status.md)。

Harness 会话把节点工作区、客户端可见性、提供方原生项目请求和独立客户端归组验证分别建模。调用方可选择 `Client` 或 `Hidden`；原生项目必须先由已经选定的 Harness 运行时探测，再显式选择该实例的已有项目或 `NoNativeProject`，不能从路径名推断，也不能跨实例复用项目 ID。`NoNativeProject` 不承诺独立客户端最终不归组。新建原生项目是独立持久操作，不随文本轮次隐式执行。项目探测或选择失败时关闭失败，不静默回退；持久请求派发后的不确定失败必须携带幂等键或已知资源 ID。

适配器工厂由可信宿主注册，配置只能引用已经编入并获准的实现。`adapter` 字段不会下载对应 SDK，`address` 字段不会安装插件、加载代码或作为任意 shell 命令执行。当前宿主提供 `remote-node` 代理，通过 `node://扩展ID` 选择已经登记的节点，并使用节点侧工作区 ID；项目探测、创建和会话结果仍按运行时能力关闭失败。独立 Harness CLI 可显式加载项目外活动配置、探测并选择项目；模拟命令不读取它，官方控制台通过可信 API 消费同一服务。直接 HTTP/WebSocket 等其他网络适配器尚未实现。

源码按 `src/<能力领域>/` 组织为单个 Cargo 包内的模块，依赖统一登记在根 manifest；各级 README 和 AGENTS 记录职责与规则。未实现领域保留规划文档，独立插件的安装与发行规则不由源码目录决定。安装数据、真实配置、日志、缓存及私有状态与源码分开，按节点和实例隔离，插件不得任意读取其他实例状态。

## 实例生命周期

真实 Harness/扩展服务现由 `boot::host::HostRuntime` 注册到 framework，并供 CLI/API 共用。服务依赖按扩展→Harness→绑定排序，关闭通过通用取消范围先拒绝新调用、取消并排空现有调用，再撤销服务；调用方退出不提前释放仍在执行的提供方。排空超时报告失败并保留待清理状态。下述完整插件升级、重启和远端事实核验流程仍包含未实现的目标要求，不能由当前共享装配推断全部支持。

概念阶段为登记、等待依赖、启动、就绪、排空、停止；故障和禁用单独记录原因。实际状态名称在实现时固定，包安装状态不与运行实例状态混为一谈。

1. 校验注册来源、配置、权限、版本和依赖图，确定作用域及提供方。
2. 按依赖顺序初始化服务；内置模块调用已注册构造入口，宿主侧外部插件由运行后端启动并握手，独立节点由其部署系统启动后按接入配置完成认证与能力匹配。
3. 通过初始化、必要探测及业务前置条件后发布可用能力；进程存在或一次心跳不代表所有能力可用。
4. 停用或依赖失效时停止新派发，处理已有调用，保存已知和未知执行事实。
5. 逆依赖顺序撤销注册，清理监听器、定时器、后台任务、连接和所属临时资源。
6. 所属运行后端停止工作进程并回收子进程；远端由节点报告并核验执行边界是否失效，宿主不能用断线代替回收证据。确认旧执行者无法继续操作后才交还锁或授予新执行权。
7. 重启有次数、退避和时间上限；持续失败禁用受影响实例并报告原因，不无限重启。

外部 Harness 节点不是由 registry JSON 动态安装的插件包。Registry 构建实例时校验配置、工厂、节点地址和工作区声明；扩展注册表再启动或连接已经安装的节点。通用调用按设置请求 `Client` 或 `Hidden` 会话；选择已有项目时先读取核对，再传入原生项目 ID 并验证返回关联。取消调用不会撤销可能已经创建的持久资源。同一实例按角色使用独立容量。未注册工具、原生命令、提供方文件修改和原生审批请求均被拒绝；只有执行会话可以请求宿主显式注册的工具，文本 CLI 与审批会话不提供工具。

同进程模块必须合作式停止并释放资源；无法安全停止时可能需要排空并重启宿主。不能强行卸载任意正在运行的 Rust 模块，也不能靠捕获 panic 隔离死锁、进程终止或原生依赖故障。

## 进程外握手与代理

对宿主启动的外部插件实例，宿主将已验证包产物、运行身份及连接通道绑定到本次启动，不能仅接受对方自报的插件标识。独立部署的节点由节点项目启动，宿主按接入配置核验对端身份、实例代次及节点范围；建立连接不意味着宿主负责其安装或启动。

双方协商协议版本、实例身份、服务版本和能力，注册能力不得超出已批准描述与配置。主版本不兼容或必要能力缺失时拒绝激活；兼容协商不能静默丢弃授权或副作用相关的必需字段。

协议代理将领域接口映射为跨边界消息，至少携带调用关联、任务和操作标识、实例、截止时间、必要授权引用及结构化结果。编码、传输、认证和大体积证据传递方式待实现验证后选择。

- 延迟、超时、断连与取消是显式结果，不能伪装成本地无失败调用。
- 发送取消请求不证明操作未发生；取消确认仍需核验已开始的副作用。
- 对消息大小、输出、速率、并发、队列及证据引用设置限额；禁止不受限地将画面塞入控制消息。
- 代理本身不生成授权。执行边界在副作用前核验任务版本、目标范围、有效授权及执行令牌；跨插件调用不通过私有通道规避这些规则。
- 断线重连需核对实例和在途调用，不将旧请求直接当作新任务重放。

## 故障范围与权限落实

可信内置模块共享宿主地址空间和故障范围；复杂原生接口、桌面会话、视觉及第三方运行时默认隔离到工作进程。按信任、资源和会话划分边界，不能把“每项服务一个进程”写成要求。共享工作进程中的能力须说明共同失效范围。

进程隔离不是安全沙箱。外部插件若继承广泛系统权限，仍可能产生未授权副作用；必须以运行身份、文件权限、凭据范围和所选平台机制落实限制。同进程模块在宿主信任边界内，框架接口不能约束任意恶意本机代码。

外部节点维护本机执行记录并监督所属工作进程，宿主运行后端监督自己启动的插件进程；系统服务机制监督宿主自身。Recuvora 程序、插件安装目录、授权策略和启用配置不向修复 AI 授予写权限。节点按平台检查 Windows 用户会话、macOS 权限、Linux 显示后端，会话变化后不能沿用旧的可用性结论。

插件失败不证明外部动作未发生。回执缺失先查询实际状态，不可安全重复的点击、发送和部署保持未知并转核验或人工处理。锁不能仅凭超时释放给新执行者，需确认旧执行边界失效。

监控过期报告覆盖缺失；知识故障暂停相关检索或沉淀，但权威记录仍用于恢复；通知失败单独记录，不改变已持久化的任务结果。各类队列均有容量和保留策略，知识补交不能重放已经完成的修复。

## 配置变更、重启与升级

| 变更类型 | 处理要求 |
| --- | --- |
| 配置修改或内置实现切换 | 校验依赖、作用域与权限并按约定排空；内置切换限已编入实现，外部绑定限经核验、获准且兼容的插件与节点 |
| 实例重启 | 保存并核验在途结果，清理资源；外部实例重新握手和探测 |
| 独立插件升级 | 固定版本，验证兼容及私有状态迁移，排空旧实例后切换；未决操作不盲目迁移重放 |
| 宿主及可信业务升级 | 受控停机、备份和恢复对账；验证权威记录迁移与节点兼容，不承诺任意热替换 |

卸载先停用并处理活跃依赖；实例私有数据按策略保留，不能级联删除权威审计或已引用证据。降级或回滚前检查状态格式及备份恢复路径，无法安全迁移时保持暂停并报告所需处理。

## 实施验收与参考

通用框架已有可信内置提供方切换、依赖检查、事件及资源清理测试；Harness 和受限修复进一步提供命名实例、工作区范围、独立审批角色、宿主工具路由、持久审批及文件动作的验证入口。当前自动通过范围以 [测试记录](../tests/README.md) 为准，受限协议夹具不能证明完整业务恢复。远端代理已有有界实现；目标专属远程部署、其他本机平台、生产进程树监督、会话变化及升级恢复仍需对应集成项目验收。控制台当前只提供单操作员令牌认证，不声明完整多用户身份系统。

每个实际插件说明服务范围、运行位置、共同失效范围、配置权限、外部副作用、幂等核验、清理及恢复策略。支持平台与稳定性结论只能依据实际验证，不以文档或目录代替测试结果。

外部扩展接入验收还应覆盖：新业务契约由插件注册及消费、命名空间冲突、缺失消费者、不兼容 schema、跨实例错误回执、权限拒绝、消息过载，以及插件/节点独立升级时的排空与未知结果核对。节点独立验证本机采集或执行实现；宿主验证接入契约和可信公共边界。当前进程夹具已覆盖注册/消费、命名空间、schema、权限、关联、容量与 Unknown；独立升级、真实跨机监督和长期资源验证仍需补齐。

审批角色与执行权限在 Recuvora 契约中独立建模。宿主只通过显式注册工具落实目标范围、持久授权和一次执行边界；任何提供方原生批准响应都不能替代 Recuvora 的完整业务授权或恢复事实。
